# 食材 v4 测试数据逻辑删除（临时）

用户 2026-10-12 重新定义了本 skill，取代 2026-10-06「全部新旧食材、餐饮商品与订单、上传文件物理清空」的旧范围：

1. **只处理名字以 `fnb_v4_` 开头的表。** `fnb_unit`、餐饮商品与分类、销售订单与支付、上传记录、S3 及服务器上的文件、员工与其他业务都不在范围内。
2. **只做逻辑删除。** 把 `valid` 置 0，同时刷新更新时间；不执行 DELETE。

该定义只适用于正式上线前。

## 范围细节

- v4 表没有 `update_date` 列，对应的是 `updated_at`，写数据库服务器的 UTC 时间，与接口自己停用记录的做法一致。表里若有 `update_date` 也一并刷新；两列都没有的表只改 `valid`。
- 2026-10-12 用户决定给原本没有 `valid` 的 21 张 v4 表补上该列（[增量 SQL](../../../sql/2026-10-12_fnb_v4_add_valid.sql)，生产已执行），所以现在 31 张 v4 表都会被处理。
- 接口从 SnowmeetApi `ai@fe4eb6c2`（2026-10-12 23:04 发布）起认全部 31 张表的 `valid`：后补 `valid` 的表查询只看有效行，逻辑删除后的批次、库存流水、单据、订单、配方、检查单在界面和报表里不再出现；批号、检查单日期、外部订单号、订单导入去重键、工具资产编号可以重新使用。幂等记录 `fnb_v4_request` 是例外，照样置 0 但接口不过滤。详见操作参考。
- 服务器上的接口版本早于 `fe4eb6c2` 时不要执行：那时这 21 张表里 `valid=0` 的行接口照样读得到。
- 以后新增的 `fnb_v4_` 表如果没有 `valid` 列，脚本会原样保留并在预览和结果里列出行数。不得为了清干净改成物理删除；加列或其他做法先问用户。
- 已经是 `valid=0` 的行不动，更新时间保持原值。
- 行数、表结构、索引、ID 序号都不变。

## 生命周期

每次使用先查看本目录 `lifecycle.json`，并核对用户最新的上线说明及项目记录。`status=testing` 才允许预览和执行；缺失、无效或 `retired` 一律停止。测试版本部署不等于正式上线。

用户明确食材系统正式上线时，或项目记录已标明正式上线时，先执行 `scripts/clear_test_data.py --retire`，将生命周期变更提交并推送到文档仓库 main，然后停止使用。退役不连接数据库；重复退役安全。不得将状态改回 testing，也不得通过复制脚本、修改检查或旧版副本继续使用。

## 执行

1. 阅读 [references/operations.md](references/operations.md)，确认目标库和范围。源码及状态随 `snowmeet_ai_doc` 仓库同步；执行前同步 main，遇到生命周期冲突采用 retired 状态。不要使用离线旧副本，尤其不要使用 2026-10-12 之前会物理删除的版本。
2. 区分请求：创建/修改 skill、查看脚本、查看范围不授权实际执行。用户明确要求执行时，在执行前确认该请求仍覆盖目标数据库。
3. 只通过明确的 `SNOWMEET_FNB_CLEAR_DSN` 连接目标；脚本绝不读取 `SnowmeetApi/config.sqlServer`，不启动 API，不执行或 import `run_fnb_http_smoke.py`。连接串来源由用户指定。先运行默认预览，向用户提供每张表要置为无效的行数，以及没有 `valid` 列而保留的表和行数；范围符合当前已授权请求就继续 `--execute`，无需重复询问。仅要求查看时停在预览。
4. 目标表按前缀从数据库目录读取。出现非 dbo 的 `fnb_v4_` 表、`valid` 列类型异常或目标表上有启用的触发器时脚本拒绝，报告具体阻碍；不得关闭检查。全部更新在单个 Serializable 事务内完成，任何一步失败整体回滚。
5. 汇报实际结果：每张表置为无效的行数、保留未动的表、清单路径和本次写入的时间戳。没有实际执行就明确说明。凭据和清单不提交 Git。

脚本路径相对本 skill：`scripts/clear_test_data.py`。默认只预览，`--execute` 执行，`--status` 查看状态，`--retire` 作废；没有重新启用选项。恢复方法、验证方式见参考文件。

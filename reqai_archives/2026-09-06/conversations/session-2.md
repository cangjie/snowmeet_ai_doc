## 结论

建议把它设计成“**门店营业班次 + 可配置任务清单 + 开关门校验**”，不要只在门店表上增加一个 `is_open`。

核心流程：

1. 店员选择当前门店，执行“开门”。
2. 系统创建本次营业班次，并按门店配置生成开门任务。
3. 开门后门店进入营业中，但持续提示未完成的开门任务。
4. 营业期间可以执行盘点、设备检查、交接等通用任务。
5. 点击“关门”时，服务端统一检查：
   - 必做的开门任务是否完成；
   - 必做的关门任务是否完成；
   - 当日续租订单是否全部确认——已有业务规则明确“未确认完续租订单，店铺不能关门”[[C4]]；
   - 其他后续配置的关门阻断项。
6. 只有全部通过，才能确认关门；否则返回明确的未完成清单。

## 已经有什么

### 可以复用的能力和交互模式

项目已经存在比较完整的“任务实例—开始—完成—中止—记录执行人和时间”的模式，但目前是**养护装备级任务**，不是门店营业任务：

- 养护任务使用 `care_task`，已存在 `task_name`、`sort`、`status`、`start_time`、`end_time`、`staff_id`、`memo` 等语义，并按任务顺序展示[[C10]][[C14]][[C17]]。
- 现有任务状态至少包括 `未开始`、`已开始`、`已完成`、`强行中止`；开始和结束动作会记录实际执行时间，其他店员执行中的任务需要走强行中止确认[[C14]][[C17]]。
- 安全检查已经采用“必填项校验 → 确认责任 → 保存数据 → 完成任务”的模式，可参考到盘点任务的提交确认中[[C2]]。
- 现有养护详情页已经有当前任务高亮、计时提醒、任务时间线、执行人展示等交互，可复用其产品模式[[C17]][[C20]]。

但**不建议直接复用 `care_task` 表**：它属于具体 `care` 的养护流程，并且存在发板、热蜡、安检等专属后端副作用[[C10]][[C16]][[C20]]。门店任务应使用独立的营业班次和任务实例，只复用交互、状态机及审计思路。

因此目前不能直接指定真实表名或复用接口；这部分必须先查代码和生产库 schema。现有资料只明确记录了续租订单对关门的阻断规则[[C4]]。

## 建议的业务模型

### 1. 营业班次

每次开门创建一条门店营业班次，建议概念名为 `shop_shift`（新名称，最终需结合现有 schema 确认）：

- `shop_id`
- `business_date`
- `status`：`opening` / `open` / `closing` / `closed`
- `opened_at`
- `opened_by`
- `closed_at`
- `closed_by`
- `close_memo`
- `version`：用于防止两名店员同时开门或关门

同一门店同一时刻只能存在一个未关闭班次。

这里建议使用“班次”而不是单纯按自然日记录，因为门店可能跨零点营业、异常补关门或一天多次开关门。（建议，文档无记载）

### 2. 任务模板

任务不能只做“盘点”类型，因为需求已经说明“盘点但不限于”。建议配置为通用模板：

- 所属门店；
- 阶段：`opening` / `during_business` / `closing`；
- 任务名称；
- 任务类型：清单确认、数量盘点、金额录入、拍照、文本说明等；
- 是否必做；
- 排序；
- 是否启用；
- 允许执行的岗位或权限；
- 是否需要复核；
- 异常是否阻断关门。

例如：

- 开门：现金备用金盘点、租赁装备盘点、打印机检查、收银设备检查；
- 营业中：临时巡检、耗材补充；
- 关门：未归还装备盘点、现金核对、门窗水电检查、续租订单确认。

以上任务名称只是建议示例，文档没有现成配置。

### 3. 任务实例

开门时把当时有效的模板复制为本次班次任务，避免管理员之后修改模板，导致历史班次任务发生变化。

建议实例至少保留：

- `shift_id`
- `template_id`
- `phase`
- `task_name`
- `task_type`
- `required`
- `status`
- `sort`
- `result_value`
- `memo`
- `started_at`
- `started_by`
- `completed_at`
- `completed_by`
- `terminated_at`
- `terminated_by`

任务状态可参考现有养护任务的 `未开始`、`已开始`、`已完成`、`强行中止`，保持后台操作认知一致[[C14]][[C17]]。但对门店必做任务，`强行中止`默认不应等同于完成，否则会绕过关门门槛；如确需豁免，应增加独立的“豁免”动作并记录授权人和原因。（建议，文档无记载）

## 开关门规则

### 开门

建议流程：

1. 服务端检查该门店是否已有未关闭班次。
2. 没有则创建班次和开门任务实例。
3. 记录开门人和开门时间。
4. 返回本班次全部任务。
5. 门店立即进入营业状态，但标记“开门任务未完成”。

按照当前描述，“开门后，需要完成任务”，因此不建议要求任务全部完成后才允许开门；否则实际语义会变成“完成任务后开门”。如果业务实际需要后者，应增加 `opening` 状态：先开始开门流程，全部必做开门任务完成后才转为 `open`。

### 关门预检

点击“关门”时先做服务端预检，不能只靠前端按钮置灰。建议检查：

- 是否存在有效营业班次；
- 必做开门任务是否全部完成；
- 必做关门任务是否全部完成；
- 是否存在异常但未处理的任务；
- 是否仍有未确认续租订单；这是已有明确阻断规则[[C4]]；
- 是否存在其他门店级阻断项。

预检失败时返回结构化阻断项，例如：

- `OPENING_TASK_PENDING`
- `CLOSING_TASK_PENDING`
- `RENEWAL_ORDER_PENDING`
- `TASK_EXCEPTION_PENDING`

前端直接展示：

> 暂时不能关门  
> · 关门任务“现金核对”未完成  
> · 还有 3 笔续租订单未确认

并允许点击阻断项进入对应任务或订单列表。

### 确认关门

预检通过后：

1. 二次确认；
2. 服务端在事务中再次执行全部校验；
3. 更新班次为 `closed`；
4. 记录关门人、关门时间和备注；
5. 保存关门时的校验结果快照。

必须在提交关门时重新校验，避免店员打开确认弹窗后又产生新的未确认续租订单。（建议，文档无记载）

## 已确认业务规则

### 1. 开门

- 所有岗位均可开门。
- 点击开门后，门店立即进入“营业中”，可以马上开单。
- 开门动作同时创建本次营业班次，并生成该门店适用的开门任务。
- 开门任务允许开门后补做，不阻断开单。
- 同一门店已有未关闭班次时，不允许重复开门。
- 门店存在跨零点营业，因此班次不能按自然日零点自动结束，也不能用“当天是否开门”简单判断。

### 2. 任务执行

- 任务分为：
  - 开门任务；
  - 营业中任务；
  - 关门任务。
- 多名员工可以并行执行不同任务。
- 盘点差异只记录，不因存在差异阻断关门。
- 必做任务有两种满足方式：
  - 正常完成；
  - 店长豁免。
- 豁免后，该任务视为满足关门条件，但必须保留豁免人、豁免时间和豁免原因。
- “强行中止”不能等同于“完成”或“豁免”。

现有养护任务已经有开始、完成、强行中止、执行人和实际时间记录，可复用其状态机与交互思路，但不能直接复用 `care_task`，因为它属于具体养护装备流程[[C6]][[C20]]。

### 3. 关门

所有岗位均可发起和确认关门。

关门时，服务端必须检查：

1. 本班次全部必做开门任务已经完成或被豁免；
2. 本班次全部必做关门任务已经完成或被豁免；
3. 如果配置了必做营业中任务，这些任务也已经完成或被豁免；
4. 该门店所有未确认续租订单数量为 0。

“未确认完续租订单，店铺不能关门”是已有明确业务规则[[C1]]。本轮进一步确认口径为：**该门店所有未确认订单，不限本班次、不限当天、不限是否跨零点**。

盘点差异只作为任务结果保存：

- `difference = 0`：无差异；
- `difference != 0`：记录差异数量、说明和附件；
- 只要任务已经提交完成，差异本身不阻断关门。

### 4. 权限

| 操作 | 权限 |
|---|---|
| 查看本门店营业状态及任务 | 所有岗位 |
| 开门 | 所有岗位 |
| 执行任务 | 所有岗位 |
| 关门 | 所有岗位 |
| 豁免必做任务 | 店长及以上 |
| 配置任务模板 | `title_level >= 300` |

现有代码记录的等级口径为：`100=店员`、`200=店长`、`300=系统管理员`、`1000=超管`[[C5]]。因此：

- 豁免权限建议使用 `title_level >= 200`；
- 模板配置使用用户确认的 `title_level >= 300`；
- 开关门与执行任务应按“有效员工身份”判断，而不是简单写成 `title_level >= 100`，避免未来新增岗位等级后被意外挡住。（建议，资料没有有效员工统一鉴权方法的代码）

## 建议状态模型

### 营业班次状态

建议概念状态如下，实际字段名需查代码与生产库 schema 后确定：

| 状态 | 含义 |
|---|---|
| `open` | 已开门，正常营业；任务可以继续补做 |
| `closing` | 正在处理关门任务，但仍未真正关门 |
| `closed` | 所有关门条件满足并已确认关门 |

不建议增加“开门准备中”，因为已经确认点击开门后必须立刻能够开单。

`closing` 不应禁止继续开单，否则员工误点“准备关门”会影响正常营业。真正的营业状态只在最终关门事务成功后变为 `closed`。（建议，文档无记载）

### 任务状态

建议沿用现有任务认知：

- `未开始`
- `已开始`
- `已完成`
- `强行中止`
- `已豁免`

现有养护任务已经使用 `已开始`、`已完成`、`强行中止`，并记录执行人及开始时间[[C20]]；`已豁免`是本功能新增状态。

关门满足条件：

```text
非必做任务
OR status = 已完成
OR status = 已豁免
```

以下状态不满足：

```text
未开始
已开始
强行中止
```

## 跨零点处理

班次必须以开门、关门时间确定边界，而不是以日期确定：

- 9 月 6 日 20:00 开门；
- 9 月 7 日 02:00 关门；
- 仍然属于同一个营业班次；
- `business_date` 可记为开门日期 `2026-09-06`，但只用于展示和统计，不能作为是否已关门的判断依据。

建议历史记录同时显示：

- 营业日期；
- 实际开门时间；
- 实际关门时间；
- 营业时长；
- 是否跨零点。

## 任务模板规则

模板配置仅允许 `title_level >= 300`。

每个模板建议配置：

- 适用门店；
- 阶段：`opening` / `during_business` / `closing`；
- 任务名称；
- 任务类型；
- 是否必做；
- 排序；
- 是否启用；
- 是否允许多人分别提交；
- 结果录入规则；
- 生效时间。

任务类型至少包括：

- 确认项；
- 数量盘点；
- 金额盘点；
- 文本记录；
- 拍照；
- 清单逐项确认。

开门时应复制模板形成班次任务快照。管理员之后修改模板，只影响后续新班次，不能改变已经开门班次的任务和历史记录。

## 豁免规则

店长豁免时必须：

1. 确认当前操作人 `title_level >= 200`；
2. 填写豁免原因；
3. 记录原任务状态；
4. 记录 `exempted_by`、`exempted_at`、`exempt_reason`；
5. 任务展示“已豁免”，不能伪装成“已完成”。

建议只允许豁免**任务**，不允许豁免“未确认续租订单”这一业务阻断项。用户本轮确认的是“必做任务可以由店长豁免”，而续租订单属于独立的关门阻断规则[[C1]]；若需要店长强制带未确认续租订单关门，应另行明确，不能默认放开。

## 关门接口必须返回的阻断项

关门预检和最终关门应使用同一套服务端校验逻辑，避免页面显示可关门、提交时口径不一致。

建议返回：

- 未完成必做任务；
- 进行中的必做任务；
- 被强行中止但未处理的必做任务；
- 未确认续租订单数量；
- 对应任务或订单列表入口。

示例展示：

> 暂时不能关门  
> · 开门任务“备用金盘点”未完成  
> · 关门任务“租赁装备盘点”执行中  
> · 当前门店还有 3 笔未确认续租订单

最终确认关门时必须再次校验，不能只依赖此前的预检结果。

## 当前复用与核实边界

目前可以确认的复用点：

- 养护详情页已有任务开始、完成、强行中止、执行人和耗时交互[[C20]]；
- 安全检查已有“校验必填数据—责任确认—保存结果—完成任务”的事务顺序，可参考盘点任务提交[[C6]]；
- 现有角色等级包括店员 100、店长 200、管理员 300、超管 1000[[C5]]。

目前资料没有提供以下代码或生产库 schema，尚不能确定真实实现名称：

- 门店营业状态是否已有字段；
- 是否已有通用任务模板表；
- 门店班次表是否已经存在；
- 续租订单的真实表、状态字段和查询接口；
- “有效员工”的统一鉴权方法；
- 门店数据是通过 `shop_id` 还是其他关联确定。

项目已有 `shop_list` 的文档记录，并且历史代码已逐步从自由文本门店名归一到 `shop_id → shop_list`[[C9]][[C10]]；但本次没有拿到对应代码模型和生产 schema，实施前仍需核实，不能仅凭文档直接定表结构。

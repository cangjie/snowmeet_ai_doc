## 流程

养护开单 → 添加装备 → 点击“添加装备”下方的“添加卡类” → 选择次卡/季卡及数量 → 查看服务、装备、扣次、余额和卡款试算 → 确认进入零售单结算 → 付清卡款 → 自动发卡、养护扣次、生效任务。

零售订单收全部卡款，独立养护订单应收为 0。新卡与两单归开单顾客。只有打蜡季卡绑定雪板；取消养护按实际核销返次，含卡销售订单一律不退款。

## 复用现有结构

| 现有记录或字段 | 用途 |
|---|---|
| order | 原养护草稿和购卡零售草稿/正式订单；沿用有效、接待中、生效、已支付等状态 |
| order.order_source / source_order_no | 零售单来源标记 care_card_reception 及原养护单 ID；没有新增字段 |
| retail | 每张实际购买的卡一行，商品、原价、成交价及 punch_card_id 继续沿用 |
| retail.memo | 付款前临时保存本次使用安排及待发卡权益；发卡、扣次和养护生效事务全部完成后清空 |
| punch_card | 实际发出的会员卡及权益；source_retail_id 指向销售明细 |
| care.card_id | 本件养护实际使用的会员卡 |
| punch_card_used | 实际扣次及取消返次的唯一核销依据，保留撤销记录 |
| core_data_mod_log | 沿用原有审计日志 |

预览只读。确认选择时保存现有零售草稿和销售明细，不创建会员卡；提交把同一草稿转为正式零售单。重复提交复用原订单，不另外生成业务关联表。

顾客自助买卡和养护开单买卡共用 `RetailCardService.GrantAsync`，使用原来的 `retail.punch_card_id` 防重发卡。养护沿用 `EffectCareOrder` 和 `punch_card_used` 防重扣次。SQL Server 事务级应用锁保护重复通知、提交与取消，不另增防重表。

支付成功后的业务处理在一个事务内完成：确认足额实收 → 按销售行发卡 → 回填 care.card_id → 核销次数/生成任务 → 更新原订单完成状态 → 清空临时安排。若实收成功但业务事务失败，临时安排仍保留，可从新请求或服务重启后继续处理，不要求再次收款。已经完成后，查单、重复通知和取消返次只依赖原有业务记录。普通订单详情不返回内部临时 JSON，避免把处理安排显示成顾客备注。

此前[三表 SQL 文件](../sql/2026-10-24_care_card_sale.sql)已经撤回建表内容，仅留下作废说明，不能再按旧说明执行三表方案。本轮没有创建或删除任何生产表。

## 接口与旧版兼容

新增 `api/CareCardSale/{action}`，沿用 `sessionKey` 与可选 `sessionType`。员工至少 100 级，原开单人或 200 级以上员工可操作指定养护单。

| 方法 | action | 请求或用途 |
|---|---|---|
| GET | GetProducts | 返回开关状态与上架养护卡商品 |
| GET | GetDraft | query: orderId；恢复选择或查询付款后结果 |
| POST | Preview | body: `{ "orderId": 123, "selections": [{ "productId": 456, "quantity": 1 }] }`；只读试算 |
| POST | SaveDraft | 同上；复用零售草稿保存临时安排；空 selections 清空选择 |
| POST | Submit | body: `{ "orderId": 123 }`；返回零售 orderId 和 careOrderId；重复请求复用原单 |
| POST | RetryCompletion | query: orderId（养护单）；仅补全已有实收，不再次付款 |

原客户端接口不增加必填参数，查单只增加可选 `careCardSale` 响应信息。原普通订单和自助购卡继续沿用原路径。取消新增表后，部署此功能不需要数据库结构升级。

旧客户端对含卡订单请求退款时会被明确拒绝，取消养护执行返次；这两项是用户确认的业务规则变化。关联养护不能提前 0 元核销或重复收款，已提交组合不能直接覆盖归属和金额。未核验顾客须本人微信付款，或先核验再用其他方式；已核验可代付，两单和卡仍归原顾客。

## 配置与发布

新入口默认关闭，读取标准配置 `CareCardSale:Enabled`：

```json
{
  "CareCardSale": {
    "Enabled": true
  }
}
```

也可以使用环境变量 `CareCardSale__Enabled=true`。仓库没有默认开启。当前生产通过 systemd drop-in `/etc/systemd/system/mini.snowmeet.top.service.d/care-card-sale.conf` 设置 `CareCardSale__Enabled=true`，已在本次部署生效。

1. 无需执行 SQL。先部署服务端并保持购卡入口关闭。
2. 用实际在用旧版验证普通开单、已有卡券、自助买卡、付款、取消及禁退，再上传新小程序并启用入口。
3. 停用入口后，已产生交易的查单、支付通知和补处理继续可用；不要直接回退到不理解购卡依赖的旧后端。

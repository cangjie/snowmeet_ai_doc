# 养护开单内购卡并用于本次养护

日期：2026-10-24。状态：按用户最新要求修订为复用现有业务表，不增加三张关联表或新列，无需执行 SQL。实现与验证细节见[实施说明](../../2026-10-24-care-card-sale-implementation.md)。服务端 `542f7074` 已部署，小程序 `2279d68c` 已推送，尚未上传发布。

## 已确认规则

1. 正常养护开单、添加装备，在“添加装备”正下方增加“添加卡类”。整单选择养护次卡或季卡及数量，查看试算后进入结算，不在每件装备内另开购买流程。
2. 购卡是独立零售订单，养护是原有独立养护订单。一次付清全部购卡款，养护应收 0；本期不合并额外收费养护。
3. 付款成功后自动发卡、扣减本次使用次数并生成养护任务。未实际付款不创建可用卡、不真实扣次。
4. 新卡与两张订单固定归开单顾客；代付不改变归属。
5. 只有打蜡季卡绑定雪板，其他卡均不绑定；季卡每日限用仍沿用原规则。
6. 含卡销售订单不允许退款，未使用或养护取消返次后也不退款。
7. 取消养护按实际有效核销记录返次；重复取消不多返，重放支付通知不重扣；季卡撤销有效使用占用，保留绑定。
8. 用户确认复用原有下单、支付发卡和养护核销逻辑，不另建长期编排数据。付款前使用安排可临时保存，业务完成后清理。

## 试算与操作

- 展示每张卡名称、售价、数量、本次服务和装备、拟扣次数、剩余次数、总卡款及养护应收 0。
- 例如 600 元 10 次卡用于两块板：零售收 600、养护 0，付款后扣 2 次余 8 次；取消一块返 1 次，购卡款不退。
- 按可覆盖项目较少的卡优先、再按选购行顺序自动分配，并逐张显示安排供确认。同种商品买两张就实际发两张；未用于本次的卡显示购买后留存。
- 每件装备的已有卡、券和本次新卡互斥；原有权益也必须足额覆盖本件养护。超权益、次数不足或额外收费明确拒绝，不默认为免费。
- 保留明确选择的项目。未选项目时，机打蜡季卡默认机打蜡、热蜡季卡默认热蜡、双项卡默认修刃＋热蜡，必须先在试算显示，提交确认才保存；单项卡不猜项目。
- 改装备、商品或数量重新试算；异步旧响应不覆盖新选择。商品变价或安排变化须重新确认，下单后清空下一单的购卡意向。

## 复用数据和支付处理

| 原业务数据 | 处理 |
|---|---|
| order | 原养护草稿与零售草稿转正式订单，完成状态沿用 dealed 等原字段 |
| order.order_source / source_order_no | 零售单记录由哪张养护单发起，复用已有来源字段 |
| retail | 一张卡一行销售记录，复用商品、成交价与 punch_card_id |
| retail.memo | 付款前临时保存待发卡权益和养护安排，业务事务完成后清空 |
| punch_card / source_retail_id | 原发卡记录及销售来源 |
| care.card_id / punch_card_used | 原养护用卡关系、实际核销与撤销 |
| core_data_mod_log | 原审计日志记录取消原因和返次变化 |

只读预览 → 保存原零售草稿和临时安排 → 确认两单 → 收零售卡款 → 原发卡方法 → 回填养护卡 → 原养护核销与任务 → 原订单标记完成 → 清空临时安排。

发卡和养护生效在同一业务事务内完成；银行实收先成功而业务失败时，保留临时安排并重试，不能要求顾客再付。支付回调、重复提交、取消使用数据库事务与应用锁串行处理。付款完成后的追溯使用原有销售、卡和核销数据。

之前提出的三张永久关联表不是本需求的必要条件，已撤回其 SQL 和 ORM 映射，不部署、不执行。

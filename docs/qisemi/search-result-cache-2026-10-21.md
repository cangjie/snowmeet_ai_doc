# 七色米搜索结果缓存：实现与本机验证

日期：2026-10-21。状态：**已实现并完成本机验证，尚未部署**。代码为 `SnowmeetApi ai@1394cbfe`，基线为 `af2b9e4c`。本轮没有改生产服务、数据库结构、抓取或导入任务。

## 用户可见行为

首次搜索建立完整匹配结果；同一主条件下，点击结果分类、结果仓库、切换名称/顶级分类排序或翻页，都从服务端缓存筛选、统计并取当前页。H5 继续调用 `Inventory`，手机只接收当前页及汇总，不下载全目录。

分类括号仍为去重“款”，仓库括号仍为全部有效尺码的账面“件”。两组标签互相影响、各自排除自身选择；统计覆盖全部页。负库存抵扣、未知数量、完整仓缺行推零、同款全部尺码和数据库排序规则均保留。商品详情、矩阵、流水和图片使用原接口，未纳入这份搜索缓存。

## 缓存与失效

- 位置：`Startup` 注册的单例 `QisemiInventoryCache`，仅当前 API 进程内存，重启清空，不持久化到磁盘或数据库。
- 身份：数据库服务器及库名、数据源、库存发布批次、依赖表版本指纹、规范化关键词，以及 `warehouseId,topCategoryId,inStockOnly,skuId,styleId,categoryId,negativeOnly,sourceEnabled,sourceDeleted`。
- `resultCategoryId,resultWarehouseId,sortBy,sortDirection,page,pageSize` 不进入身份；这些操作复用同一完整结果。
- 完成构建后绝对有效期 5 分钟；最多 32 项，存储体积按序列化大小乘 4 再加固定开销估算，预算 64 MiB，超预算单项正常返回但不保存。采用 LRU 淘汰；估算预算不等于进程实际内存上限。
- 同键并发复用一次成功构建；不同键最多同时构建 2 份。失败、取消、构建期间版本变化的结果不保存；等待者取消不会取消正在为其他请求构建的结果。
- 每次请求仍先检查有效数据源、当前已发布并核对通过的批次；旧 `batchId` 保留 409。再核对同数据源 10 张依赖表的行数及最大 `row_version`：`qsm_import_batch/import_module/raw_record/product_style/product_sku/style_sku/stock_total/stock_snapshot/category/warehouse`。插入、更新、删除会改变指纹，下一次请求使用新键。逻辑删除及所属模块/原始记录失效同样生效。
- 冷构建前后再次比较指纹；沿用 RepeatableRead 读取。没有使用会被食材/零售等无关写入改变的数据库全局 `@@DBTS` 作为缓存版本。
- 新增 `Inventory?refreshCache=true` 可强制重建当前主条件；H5 既有刷新动作会携带该参数。主条件变化、版本变化、到期或淘汰后需重新构建。
- 仍按用户既定要求暂不鉴权，保留 `SessionKey/SessionType` 请求头；以后启用鉴权时必须将解析后的数据权限范围加入缓存键。未新增公开诊断路由。

缓存命中**仍会查数据库**：有效源、发布批次、依赖版本共 3 个 SELECT；含事务开始和提交，SqlClient 统计为 5 次服务器往返。版本检查只读取行数和版本列，不展开原始 JSON，不重做库存匹配、各仓有货联接或数量汇总。该检查成本随数据量增长，不能称为零 SQL 或固定耗时。

## 实现位置

- `Services/Qisemi/QisemiInventoryCache.cs`：容量、过期、并发及统计。
- `Services/Qisemi/QisemiInventorySearch.cs`：版本指纹、缓存身份、结果分类/仓库联动、排序分页。
- `Services/Qisemi/QisemiInventory.cs`：一次读取有效 SKU 所属链和窄列库存，在内存构建全尺码数量及完整搜索集合；SQL 提供名称顺序和分类双向排名，保留数据库中文排序。
- `Services/Qisemi/QisemiReadService.cs`、`QisemiContracts.cs`、`Startup.cs`：接入缓存和刷新参数。
- `wwwroot/wecom/qisemi/app.js`：显式刷新透传；`index.html` 的脚本版本为 `20261021-result-cache`。

原反复连接商品、原始记录、批次及各仓的聚合在全量本机快照上超时；本轮已改为一次有效 SKU 所属链检查、库存窄列读取及内存数量汇总，最终完整回归通过。未增加索引或执行 DDL。

## 建议与时间预算

采用“提前构建、备份并校验，最后停服务切换”的单实例发布方式。**正常预计 SnowmeetApi 不可用 30–90 秒，建议安排 5 分钟维护窗口，覆盖失败回滚。** 准备和验证的总操作时间预计 15–30 分钟，大部分期间旧服务继续运行。

这些是根据现网配置和旧版本启动日志给出的工程估算，不是新版本实测值，也不是最长停机承诺。磁盘、依赖或启动异常可能超出窗口；发生异常优先恢复旧版本，不在停机期间编译或排查业务问题。

| 阶段 | 预计耗时 | SnowmeetApi 可用性 |
| --- | --- | --- |
| 固定版本、核对容量与配置、准备回滚备份 | 3–5 分钟 | 旧服务继续运行 |
| 隔离构建 Linux 发布包、传输和完整性校验 | 5–15 分钟，网络较慢时可能更久 | 旧服务继续运行；服务器构建时监控资源占用 |
| 停止旧进程、替换发布文件、启动并检查核心接口 | **正常 30–90 秒** | **相关页面和接口暂时不可用** |
| 业务与企业微信验收、观察日志 | 5–10 分钟 | 已恢复；若发现阻断问题则回滚 |
| 切换失败时恢复原文件并重启 | 目标累计中断约 2–5 分钟 | 恢复旧版本后结束本次发布 |

正常切换内部预算：停止及等待已有请求 0–30 秒；切换文件约 5–15 秒；启动与首次健康请求约 15–45 秒。不能把所有请求都保证在此范围内：现有 systemd 的停止、启动超时各为 90 秒，长请求、WebSocket 或异常启动可能扩大中断时间。

## 影响范围

- 维护期间，所有经 5000 进程访问的 API 和 ASP.NET 托管页面都会短暂失败，包括小程序相关后台接口、食材 V4、企业微信 H5、七色米及共用 WebSocket。前端可能显示网络错误或 nginx 502，WebSocket 客户端需要重连。
- 正在处理的请求可能未完成。支付回调等共用入口也在这个影响范围内；应选择无支付、开单、出餐等关键操作的低峰时段，不在发布验收中制造实际交易。
- SQL Server、nginx、公众号的 5001 服务、`wl.snowmeet.top` 的 5002 服务和 `mini.snowmeet.com` 的 5003 服务无需重启。`/sams/` 走独立的 nginx 代理规则，也不依赖本次 API 进程切换。共机 CPU/磁盘竞争仍可能影响延迟。
- 本次不需要建表、改表或重导七色米数据：37 张表和首批数据已经迁入，新接口启动不执行迁移。数据仍是已发布的 2026-10-18 抓取快照；发布不会自动使其变为实时库存。

## 部署顺序

1. **部署授权后，先完成所有不停机准备。** 再查现网 HEAD、进程、接口、容量和是否有其他发布任务。固定 `5c966e42`，保存旧 Swagger 路径清单、运行文件哈希和配置保护清单。若线上版本已变化，先重新比较差异，不覆盖其他人的修改。
2. **保留可直接恢复的旧程序。** 按本次将覆盖的文件清单备份现网运行文件和必要静态资源，记录所有者及权限。保护现网 `config.sqlServer`、`appsettings.json`、证书私钥、上传文件、监控状态等运行资料，不以发布包覆盖。备份和日志不进入 Git。
3. **隔离构建。** 从固定提交导出干净源码，在独立目录生成 `linux-x64 / Release / self-contained` 发布包，核对与现网运行时及依赖的差异，不在本次混入未经审阅的升级。优先在构建机生成、校验后传输；若使用服务器构建，同样在独立目录并先验算峰值空间，不能对正在运行的目录直接 `publish`。任何构建或还原错误都在旧服务正常运行时解决。
4. **发布前检查。** 校验程序集、依赖清单、静态资源及哈希；确认七色米 4 个 H5 文件完整、版本参数正确。只读检查数据库连接、已发布批次和代表性数据、S3 私有文件读取条件。切换文件预先放在同一文件系统，实际包和备份落盘后至少保留 512 MiB 可用空间，并按 SQL 日志增长及当时负载上调；不足则不进入维护。预检查不算新版本线上启动验收，不直接启动会执行现有后台任务的第二个完整生产进程。
5. **进入维护窗口并计时。** 停止服务，确认旧进程退出；根据审核后的清单切换程序集、依赖描述及静态资源。各文件用暂存后替换方式落盘，避免对仍被进程映射的库直接写入。不清空项目根目录、不做整目录 `rsync --delete`，不把全程复制数百 MB 或下载动作留到此时。保持当前工作目录和服务启动路径，无需修改 nginx 或 systemd 单元。
6. **启动并判断是否恢复。** 启动原服务，依次确认监听、旧只读接口、七色米入口及真实库存请求成功。`is-active` 和“已经启动进程”不足以判定可用。目标在停止旧服务后的 90 秒内完成核心恢复检查；若启动/旧接口恢复失败或持续 5xx，立即走已准备的回滚，不现场重编译。
7. **恢复后的验收。** 对比旧 588 个路径及其操作仍在；核实新增七色米 27 个 GET 操作、入口跳转、Fischer 同款尺码与各仓数量、单据详情、图片和原表读取。检查 S3 实例角色真实访问、近期错误日志和原有食材只读请求。用企业微信手机打开最终地址，检查搜索、横向矩阵、图片和页面缓存。最后记录实际中断时间、版本、静态哈希、遗留事项。

七色米入口使用 `https://mini.snowmeet.top/wecom/qisemi`。本期继续按已批准要求保留 `SessionKey` / `SessionType` 请求头但不启用鉴权。企业微信应用菜单/首页地址若需调整，待新页面恢复且验证通过后再改，不把控制台配置耗时放入 API 停机窗口。

## 回滚方案

- **构建或预检查失败：** 不切换、不停旧服务；本次部署结束。
- **新进程启动失败或旧功能异常：** 停新进程，按备份清单恢复旧程序集、描述文件和受影响静态文件，启动旧服务，核对原接口与静态哈希。只移除本次清单中新增且旧版本不存在的文件，不清理其他运行资料。
- **七色米功能阻断且无法在恢复后的短时间内确认原因：** 同样恢复旧版本，先保障原有业务。图片首次冷加载慢与服务整体不可用分开判断；禁止用线上写交易作验收。
- 本次没有数据库迁移或业务写入，所以回滚对象是程序和静态资源，无需回滚整库，也不撤销已迁入的七色米数据。正常发布期间产生的其他业务数据必须保留。

回滚目标是累计中断约 2–5 分钟，受系统停止超时、磁盘和启动故障影响，不能视为硬上限。实际执行时分别记录停止开始、最后一次旧版成功、首次失败、首次核心接口恢复、首次七色米成功，避免仅以 systemd 的启动时间计算中断。

## 最初用户要求与交接范围（历史）

用户指出：既然是“基于搜索结果”的分类、仓库筛选，应当直接从已有结果中筛选，不必每点一次标签都重新查询数据库。解释当前分页实现后，用户要求“这个记录下来，我可能需要换个电脑来实现”。

后续目标：首次主查询取得完整匹配结果及筛选所需数量；二次分类、二次仓库筛选，以及排序、分页，尽量复用同一份结果，避免反复执行库存匹配和数量汇总 SQL。不能只筛当前页而漏掉其他页。

**缓存优化尚未实现；前端全量筛选或后端缓存的具体选型、容量和失效时间尚未定稿。** 本次要求是交接记录，不是在当前电脑继续开发或部署。

## 交接时核对的实现（历史基线）

本次按本机 `SnowmeetApi ai@af2b9e4c6016736cb43091e750acbf951d150822` 源码核对。生产版本据 [2026-10-20 部署记录](deployment-query-enhancements-2026-10-20.md) 为同一提交；本次没有重新登录生产服务器核实。

- `wwwroot/wecom/qisemi/app.js`：`result-category` / `result-warehouse` 点击更新路由并回第一页，`inventory()` 再调用 `Inventory`。切换显示仓会清理已展开的商品明细。
- `wwwroot/wecom/qisemi/api.js`：`request()` 每次发起 fetch，使用 `cache: 'no-store'`；会保存账套及库存批次，但没有保存完整搜索结果。
- `Services/Qisemi/QisemiReadService.cs`：`ReadAsync()` 每次开连接、开启 RepeatableRead 事务、核对数据源及发布批次，再执行库存查询。旧 `batchId` 与当前发布指针不符时返回 409。
- `Services/Qisemi/QisemiInventory.cs`：`Inventory()` 重做商品匹配、各仓有货集合、分类统计、仓库数量统计及分页。二次筛选后的页数据由 `sql.Page()` 返回。
- `Services/Qisemi/QisemiContracts.cs`：默认 `PageSize=30`；H5 也按每页 30 条处理。浏览器只取得当前页商品及分类/仓库汇总数字，并未取得全结果的商品分类、各仓数量与成员关系。

因此，当前标签点击确实会重新查数据库。只有当前页和汇总数字，不足以在前端正确重建跨页筛选结果。单个商品展开后的尺码、矩阵及展开区仓库名称过滤已有独立处理，不能与整份搜索结果缓存混为一谈。

## 交接时建议实现方向（历史，已完成选型）

1. 将主查询得到的完整匹配集合与“二次筛选、排序、分页”分开。缓存需要包含完整款式身份、匹配分类关系、排序字段、各仓有货成员关系、全部尺码的数量合计及未知状态；仅缓存总数和当前页不够。
2. 优先评估后端缓存完整结果、H5 仍只收当前页的方式，减少手机首次下载及内存压力。后续仍可请求接口，但从缓存筛选、汇总与分页，无需重复执行重型库存 SQL。小结果集也可评估前端全量处理，先量测再定。
3. 缓存身份至少包括数据源、库存批次与全部会改变主匹配集合的条件。现有 H5 条件为 `keyword, warehouseId, topCategoryId, inStockOnly, skuId`；兼容 API 时还要检查 `styleId, categoryId, negativeOnly, sourceEnabled, sourceDeleted`。二次条件 `resultCategoryId/resultWarehouseId`、排序和分页不应导致重新构建同一基础集合。
4. 换主条件或发布新批次时，使用新结果；保留现有 409 提示与刷新行为。显式刷新、缓存到期、容量淘汰及逻辑删除/资料变更的失效路径需要设计，不能假定同一批次下所有主数据永远不变。
5. “不重复查库”以避免重复库存匹配及数量聚合为目标。发布指针、有效性检查可能仍需轻量查询，应单独记录，不承诺所有接口零 SQL。首次请求、商品详情及私有图片/文件的读取另行计量。
6. 缓存必须有内存上限、过期及并发复用策略；未来启用鉴权时按实际数据权限隔离。继续预留 `SessionKey/SessionType` 请求头，不在本任务顺带启用鉴权。

## 必须保留的功能口径

- 完整结果先筛选、排序，再分页；分类、仓库括号覆盖全部结果页，不是当前 30 款。
- 分类括号仍为去重后的“款”，仓库括号仍为全部尺码合计的账面“件”。同款可以同时在多个仓有库存。
- 分类统计考虑二次仓库选择，并排除自身分类选择；仓库统计考虑二次分类选择，并排除自身仓库选择。保持其他可选标签及恢复“全部”的能力。
- 有货仓候选仍按同款至少一个尺码有正库存判断；选仓后的件数包含全部尺码的正负抵扣，可能为零或负数。
- “全部仓库”按来源总表或所选主仓计算，不能简单累加有货仓标签；未知数量保留未知，不能当零或部分合计。
- 同款全部尺码、零/负/未知库存、来源链有效性与逻辑删除规则继续有效。
- 默认名称升序，支持名称/顶级分类双向排序；缓存内排序须核对与既有 SQL 排序的一致性，包括中文、未分类及同名项的稳定顺序。
- 二次筛选、排序回第一页；展开尺码、矩阵、库存流水使用当前所选仓库。列表图片继续自动加载，旧请求的迟到响应不能覆盖新条件。

## 原验收清单

1. 构造超过 30 款且跨分类、跨仓、跨尺码的结果，证明二次筛选不漏第二页及后续页，计数与未优化实现一致。
2. 覆盖分类/仓库交叉切换、恢复全部、升降序、翻页；验证负数抵扣、未知数量、完整仓缺行零值及逻辑删除。
3. 用接口请求记录和 SQL 执行统计分别验证：同一主条件及批次只构建一次完整集合；后续二次筛选、排序、分页不重复执行重型库存查询。新主条件、失效及新批次按设计重建。
4. 测量首次查询及连续切换的耗时、缓存大小、并发和淘汰行为；不把“接口有请求”误判为“数据库重新全查”。
5. 补充既有 `SnowmeetApi.Tests/QisemiSqlServerTests.cs`、`QisemiSnapshotTests.cs`、`QisemiHttpContractTests.cs` 与 `SnowmeetApi.Tests/H5/qisemi.test.cjs`、`qisemi.browser.cjs` 中与本改动相关的检查；完成真实页面及企微手机验证后分别标明证据。

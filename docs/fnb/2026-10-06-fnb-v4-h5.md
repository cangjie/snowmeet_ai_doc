## 复用方式与规则

- 员工登录沿用餐饮企业微信应用（agentid 1000009）与 `fnb_mat_sessionKey`。已有企微会话直接经 `FnbAuth/GetMe` 验证在职、门店和角色；OAuth code 交给 `FnbAuth/WeComLogin`。及时清掉 URL 的 code/state/sessionKey，保留批次 id 与页面锚点。
- 非企微且无会话显示进入提示，避免 OAuth 循环。code 2 清会话并重新进入；code 3 显示权限错误；code 4 保留表单，由用户重试，不自动重复 POST。第一期写接口不改库存，不带 requestId；`FnbClient.requestId()` 供后续过账接入使用。
- GET 的 shopId 放 query，POST 放 body，由 GetMe 的真实门店赋值。long ID 不转 Number；现有主数据 int ID 按接口要求传数字。
- OCR 沿用原页面 getUserMedia 相机逐帧调用 `FnbMaterial/OcrScanName`、1300ms 节流、30 秒截止、候选多选拼接。日期/保质期直接采用服务器候选；关闭、切页、退出停止摄像头，晚到结果不填入下一页。
- 上传沿用 `FnbMaterial/UploadPhoto`，multipart 字段 file，与 API 同源；返回图片地址经 img.snowmeet.top 显示。上传未结束时不提交建档表单。
- 蓝牙/签名沿用 `BlePrint` 和 `FnbWeCom/GetJsSdkSignature`。不删除实验页和库文件。食材标签排版复用小程序 60×40mm、GB18030、TSPL 原生二维码，二维码改为统一 `/fnb/b?id=…`；标签内容只能采用服务器 GetLabelData 的成品字段。
- 换算、预计/实际出成率、到期、批号、建议作业、可出餐份数与报表行不在前端计算。百分比输入和显示只是呈现格式，实际业务计算保留在服务端。
- 店长/员工按钮按 GetMe 展示；最终权限仍由每个服务端接口检查，不允许切换成虚假店长。

## 与原型及原服务端计划的差异

1. 当前后端只实现第一期，因此完整 32 步运营流程尚不能验收。前端完成已可接通的主数据，其余只提供页面布局和输入结构，不声称完整业务交付。
2. 原型上游形态输入的是相邻换算。第一期接口目前接收 `perBase`，H5 明确让用户填写“每 1 形态单位含多少基本单位”，相邻换算展示接口返回的 `in_op_ratio`。没有在页面中自行换算。
3. 原型的模拟员工、样例库存与日期、10/02/10/05 临时粉色标记不进入产品；头部显示真实员工角色，营业日期等待首页接口提供。
4. 10/02 的存储区域、检查、工具、物资是原服务端计划排除项，本轮按新原型保留前端入口及布局，但仍无服务端支持。
5. 手动厨房单按现有服务端计划预留；美团订单导入不在本轮。

默认做法继续遵守：耗时作业提前完成仅店长；不提供作业撤销；投入可填小数；条码全局唯一；主数据跨店共享、库存/配方按店分开。当前没有实现后几期库存写接口，相关业务权限等待服务器接入。

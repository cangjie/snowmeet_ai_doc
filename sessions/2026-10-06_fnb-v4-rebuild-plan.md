## 2. 读 Claude Design 设计稿

- 用户给了 v4 原型和操作说明两个分享链接，打开需要登录 claude.ai。
- 内置浏览器第一次打开时跳到登录页，由用户本人登录（我不能代填账号密码）。
- 设计器页面本身取不到原文，改在 claude.ai 页面里用 fetch 调 `OmeletteService/ListFiles`、`GetFile`（Connect JSON 协议，返回 base64），拿到项目里所有文件的原文。项目共有 26 个文件。
- 读了以下几份：
  - `食材管理 v4.dc.html`（35 万字符）：数据都在脚本常量里（`ROUTES0`、`SUBS0`、`ITEMS0`、`PREPS0`、`DISHES0` 等），模板文字只是 `{{ }}` 占位。
  - `从零上手操作说明`：32 步，示例是帕斯雀牛肉披萨（9 寸）+ 热拿铁（400 ml），包括从零建分类、链路、规格、半成品和菜品，开业前一天入库和解冻芝士，当天备料、做饼底和出餐，收档时盘点和导出报表。
  - `食材形态流转 方案`、项目自带的 `CLAUDE.md`。
- v4 的核心模型：
  - **形态链**：采购态 → 中间态 → 出品态。相邻形态之间只走一个固定作业，作业有换算、标准出成率和可选耗时，例如马苏里拉冷藏解冻 24 小时。
  - **入库只进进货规格指定的那一层，配方和出餐只扣出品态**。
  - **进货规格**：同一种食材可以有几种买法（整箱、单桶），每种规格决定从哪一层入库；扫条码自动选中规格。
  - **作业台**：进行中的耗时作业、建议作业（出品态低于预警线时列出）、可作业批次、今日记录；它取代了原来的「开封」和「半成品制作」两个入口。
  - **二级分类属性**：批次号编码（批次号格式 yyMMdd-编码-NN）、计量方式、保质期、开封/作业后保质、临期提醒。
  - **半成品**：按每批产出 × 批数制作；新建菜品时可以给默认规格起名（如「9 寸」）；新增「出品与配方链路」报表导出。
- 原型里的提示文案体现了这些规则：
  - 改链路、改规格、新建食材需要店长；
  - 有库存的规格只能停用；
  - 必须先拍照才能加入入库单。

## 3. 盘点现有系统（两个后台只读 Explore）

- **接口**：新的库存接口统一通过 `FnbAccess.ResolveActorAsync`，已同时兼容 `wechat_mini_openid` 和 `wecom_userid` 两种会话；缺的是企业微信端没有「我是谁」接口（OAuthLogin 只返回 sessionKey 和 userid）。
- **四个已知问题仍然存在**：
  - 死锁 1205 有的接口直接返回 500；
  - 入库不拦已过期的批次；
  - `ListBatches` 没有「只看在库」过滤；
  - `PostServe` 不回写订单状态。
- **表结构的坑**：
  - 批次库存表的 CK_7 是双向约束；
  - 视图的可用量只排除整件；
  - 「可用量」有三种算法。
- **其他**：
  - 企业微信应用密钥硬编码在代码里；
  - 美团采集程序目前只把订单存在本机文件里，还没进入出餐单。

## 4. 计划的两个版本

- **第一版**（用户先定的方向）：
  - 只做 10/05 批；美团订单这次不接；
  - 分类给默认值，食材可单独改；
  - 按兼容旧数据的迭代写：表上加 `form_id` 等可空列，旧批次照常工作。
  - 对照建表脚本，校正了 CK_7、CK_9 和视图口径。
- **用户第二次决定**：「之前的数据都不需要了，推翻了重来。唯一可以复用的就是店员登录认证体系，部分表结构和 api 接口。前端几乎要推倒重来。」
- **重写后的计划**：
  - **数据库**：一份重建脚本，先删旧的 fnb 表、视图和旧提醒表，`fnb_unit` 和 `product` 不动；再按新模型建表：
    - 主数据：`fnb_category`（带二级分类属性）、`fnb_shelf_life_rule`（按季节档）、`fnb_item`、`fnb_item_form`、`fnb_purchase_spec`；
    - 门店数据：`fnb_batch`（批次状态分 sealed/staged/final 三种，数量一律按基本单位，带 `ready_at`）、单据 / 单据行 / 流水、`fnb_stock_operation`、配方、菜品规格（同一菜品下规格名唯一，为以后订单匹配做准备）、盘点、厨房单；
    - 两个视图。
  - **接口**：按 v4 页面分 12 个模块（认证、首页、分类、食材链路、入库、库存、作业台、半成品、菜品、出餐、盘点、报表），另有公共接口；核心规则全部放在服务端。
  - **双端兼容 8 条**：GetMe / WeComLogin、先定接口契约、规则只在服务端算、统一调用约定、扫码、标签链接统一、文件上传下载、权限只在服务端判断。
  - **分三期实施**；验收直接照搬 32 步写成 LocalDB 集成测试。
  - **旧的过期提醒**（mat_expire 小程序页和企业微信 H5、旧批次表）、小程序 `fnbinv` 分包一并退役。

## 学到的小知识

1. **Claude Design 文件可以经 OmeletteService 读到**：用户登录后，在 claude.ai 页面里 POST `ListFiles` / `GetFile`，请求体 `{projectId, path}`，返回 base64 原文。原型数据在脚本常量里，渲染出来的页面文字没有用。
2. **重建比兼容迭代简单得多**：不用保留旧数据，就不用照顾 `form_id IS NULL` 的老批次、双向 CHECK 约束、三套可用量口径。可用状态收敛成 sealed/staged/final 三种，「可扣」只用一个判断。
3. **额度判断要看实际读数**：`get_usage` 能读到计划额度和会话上下文。上下文很大的会话里每一轮都更贵，大活要开新会话，或者交给别的工具做。

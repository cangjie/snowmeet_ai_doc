## 官方 API 调研结论

### 美团外卖

- 商家开放能力包含已支付、已确认、已完成订单推送，以及取消、退款、配送、出餐状态等消息，可用于订单同步；具体可用能力取决于应用与门店授权。
- 当前核查的餐饮品牌直接接入标准：门店数量至少 30 家且日订单量至少 1,000 单，并满足长期增值产品合作或综合经营水平等条件之一。未满足标准时，文档提供由品牌业务经理发起特批的路径；暂不提供个人开发者对接。不能将“平台有 API”理解为任意单店都能直接开通。
- 一个门店最多一条接单绑定，可同时存在多条非接单绑定。非接单绑定取得订单功能授权并单独订阅对应回调后，可接收代运营已确认、取消、完成等订单消息；不能据此推定可接收接单主推单或全部退款回调。
- 对本项目的意义：可能保留现有收银系统接单，同时同步订单用于食材管理；具体数据覆盖范围需按门店实际授权核查。

来源：[订单推送](https://developer.waimai.meituan.com/home/doc/food/7)、[品牌入驻指南](https://developer.waimai.meituan.com/home/guide/47)、[接单与非接单](https://developer.waimai.meituan.com/home/guide/46)。本次读取了官方页面对应的公开文档数据。

### 饿了么／淘宝闪购

- 当前官方商家入口显示为“淘宝闪购服务商平台”，公开介绍提供订单、商品、门店等 API；官方既有资料包含新订单消息推送。
- 当前应用可申请的消息清单、准入条件、门店授权范围及费用未核实，不能承诺任意商家可直接开通、免费或与已有系统同时取得全部权限。
- 部分公开接入资料较旧：2017 年接入 PDF 和既有推送协议可作为历史能力依据，不能直接作为当前申请流程或审批条件。

## API 不可用时的网页采集评估

结论：存在技术上的可行路径，可保留为候选方案；尚未通过真实商家账号验证，不能当作已确定可稳定运行的方案。

本次检查了美团商家网页版及商家登录页面的公开 HTML：页面依赖动态加载，并加载了安全验证组件。没有读取到登录后的订单列表、详情或真实数据。

建议验证的流程：门店电脑正常登录美团商家后台 → 浏览器插件或浏览器自动化读取订单页面 → 上传 SnowmeetApi → 统一订单处理。

| 方式 | 自动化程度 | 实际限制 |
|---|---|---|
| 浏览器插件读取页面 | 有效登录且页面运行时自动读取、上传 | 只能读取已加载内容；可能需要展开、翻页，页面改版需适配 |
| 浏览器自动化 | 自动打开列表、进入详情和读取数据 | 需持续运行的电脑或服务器；验证弹窗、登录失效、页面变化会中断 |
| 手机截图上传 OCR | 用户上传后自动识别 | 截图上传仍需人工；截断、遗漏和识别错误需校验，适合补录 |

浏览器插件读取 DOM、自动化工具复用登录状态是通用技术能力，不能据此认定美团具体页面已经验证可用。出现重新登录或验证要求时，需要提示操作人员处理并标记同步中断，不能把中断显示为“没有新订单”。

平台限制：本次核查的《美团外卖商家版用户服务协议》限制未经平台认可的程序抓取。使用本店账号与平台认可自动采集是两项不同条件；具体采用时需核对适用条款。本记录仅描述文档限制，不作法律定性，也不将自动化方式视为官方开放 API。

## 对食材系统的设计建议

- 记录的方案优先顺序：官方 API → 网页采集候选方案 → 截图 OCR 补录。若直接接入受限，也可核查现有收银系统是否提供外卖订单接口，不能预设其一定具备此能力。
- 各来源统一进入 SnowmeetApi，小程序与企业微信 H5 共用订单数据。网页采集程序应独立运行，不依赖员工持续打开食材小程序或 H5。
- 统一按“平台＋门店＋平台订单号”识别订单，处理重复通知、重复采集以及网页与截图重复导入；缺少可靠订单标识的 OCR 结果需核对，不能无条件自动扣料。
- 建立平台菜品／规格与系统菜品／配方的映射，覆盖套餐子项、加料和数量。
- 获取订单与扣减食材分开，在约定的出餐节点扣减并防重复。取消、部分退款须结合实际是否制作处理，不能自动恢复已经消耗的食材。

## 后续启动时的验证项

1. 核查实际门店数、平台资质、现有收银系统及门店授权，确定 API 或已有收银系统接口是否可用。
2. 如评估网页路线，用一个真实门店开展只读验证，检查订单号、菜品、规格、数量、套餐、加料是否完整。
3. 覆盖翻页、历史／预订单、高峰期新增订单，以及取消、部分退款和出餐状态变化，核对是否漏读。
4. 验证登录持续性、断网恢复、同步中断提示、恢复后补采及多来源去重。
5. 验证通过后再确定网页采集能否承担日常自动同步；当前没有承诺同步延迟、准确率或无人值守时长。
